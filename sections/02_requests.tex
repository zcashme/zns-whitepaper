\section{User requests}
\label{sec:requests}

A Request asks the Mint to evaluate a name change. A Respond returns an OTP for a pending Request. Neither is a Name Note and neither binds a transition to a note commitment.

\subsection{Request encoding}

User-to-Mint memos are a 512-byte field. A parser removes the maximal trailing sequence of zero bytes. The remaining bytes MUST be UTF-8. The colon byte (\texttt{0x3a}) separates fields. The first field MUST be the exact ASCII bytes \texttt{ZNS}. Extra fields, missing fields, and empty required fields are rejected.

The name field MUST contain between 1 and 63 bytes, each of which is ASCII \texttt{a}--\texttt{z} or \texttt{0}--\texttt{9}.

A Request has one of the following forms:

\begin{center}
\texttt{ZNS:claim:<term>:<name>:<ua>}\\
\texttt{ZNS:claim:<code>:<term>:<name>:<ua>}\\
\texttt{ZNS:update:<term>:<name>:<ua>}\\
\texttt{ZNS:release:<name>:<ua>}\\
\texttt{ZNS:list:<name>:<ua>:<pay\_to>:<price>}\\
\texttt{ZNS:auction:<name>:<ua>:<pay\_to>:<start\_price>:<min\_price>:}\\
\texttt{<start\_block>:<end\_block>}\\
\texttt{ZNS:delist:<name>:<ua>}\\
\texttt{ZNS:buy:<name>:<ua>}
\end{center}

The \action{auction} form is one memo with no line break; it is wrapped here, and wherever it appears below, to fit the page.

The \texttt{<term>} field of a \action{claim} is either the exact ASCII bytes \texttt{forever} or \texttt{<N>y}, where \texttt{<N>} is a canonical decimal integer from 1 to 99 with no leading zeroes. \texttt{forever} requests a registration without fixed expiration. The \texttt{<term>} field of an \action{update} is one of: the exact ASCII bytes \texttt{none}, which carries the current \field{expires\_at} forward unchanged; \texttt{<N>y} under the same spelling rules, which requests an extension of \texttt{<N>} years; or the exact ASCII bytes \texttt{forever}, which requests an upgrade of a fixed-term registration to a registration without fixed expiration. An \action{update} MUST NOT use \texttt{forever} against a registration whose \field{expires\_at} is \texttt{none}: the upgrade applies only to a fixed-term registration. A \action{claim} MUST NOT use \texttt{none}: it says \texttt{forever}. No field of any memo is empty.

An optional leading \texttt{<code>} field may appear only on a \action{claim}. It is exactly six ASCII decimal digits, \texttt{0}--\texttt{9}, including leading zeroes. A parser that sees a leading field that parses as \texttt{forever} or \texttt{<N>y} MUST treat it as the term (the three-field claim form). Any other leading field that is exactly six decimal digits is the access code. A leading field that is neither a valid term nor a valid access code is rejected. Update and release Requests MUST NOT carry an access code. The access code is not an OTP and is never present on a Respond.

The \texttt{<ua>} field of a \action{list}, \action{auction}, or \action{delist} Request is the Unified Address currently bound to the name. The \texttt{<ua>} field of a \action{buy} Request is the buyer's Unified Address, which a resulting \action{sale} binds to the name. The listing terms \texttt{<pay\_to>}, \texttt{<price>}, \texttt{<start\_price>}, \texttt{<min\_price>}, \texttt{<start\_block>}, and \texttt{<end\_block>} are specified in Section~\ref{sec:listing-terms}. A Request MAY spell a price with trailing fractional zeroes or a trailing period; the Mint writes the canonical spelling into the Name Note. These four Requests MUST NOT carry a term or an access code.

A Respond has one of the following forms:

\begin{center}
\texttt{ZNS:otp:<otp>:<name>:<verb>:<ua>}\\
\texttt{ZNS:otp:<otp>:<name>:list:<ua>:<pay\_to>:<price>}\\
\texttt{ZNS:otp:<otp>:<name>:auction:<ua>:<pay\_to>:<start\_price>:}\\
\texttt{<min\_price>:<start\_block>:<end\_block>}
\end{center}

In the first form, \texttt{<verb>} is \texttt{update}, \texttt{release}, or \texttt{delist}. A \action{list} or \action{auction} Respond repeats the listing terms, so the controller returns exactly what it authorizes.

The Relay and the Respond have the same form and differ only in sender: the Mint sends the Relay to the controller, and the controller sends the Respond back to the Mint. The controller constructs nothing; the memo is copied back.

A Request or Respond MUST include a non-empty Unified Address. A \action{claim} is only a Request. Request and Respond memos do not encode \field{expires\_at} or \field{prev}.

An \action{update}, \action{release}, \action{list}, \action{auction}, or \action{delist} Request is the first step of the authorization procedure specified in Section~\ref{sec:authorization}. A Respond is the third step: the controller sending the OTP back to the Mint. The \texttt{<otp>} field is exactly six ASCII decimal digits, including leading zeroes. A \action{buy} Request is the first step of the purchase procedure specified in Section~\ref{sec:marketplace}; it has no Respond.

A Request parser MUST reject any memo that does not match one of the forms above, including the \texttt{otp} form. A Mint-side parser accepts the \texttt{otp} form as a Respond.
