# Context 11: User Authorization by Shielded Challenge

A valid Mint self-send proves that the Mint spending key authorized a Name Note. It does not prove that the requester could receive messages at the Unified Address whose binding was created, changed, or released. ZNS therefore requires a separate authorization exchange before the Mint creates a Name Note.

The **shielded challenge** is the existing ZNS OTP authorization mechanism. The terms **private Mint challenge** and **shielded OTP** refer to the same mechanism.

A **shielded challenge** is a secret generated by the Mint and sent in a shielded memo to a receiver selected from an authorization Unified Address. A **successful response** returns the expected secret to the Mint through a separate shielded message.

PIR is proposed custom cryptography for name circuits. It is not part of the shielded challenge defined here.

This document introduces only the OTP authorization exchange. It does not define name availability, pricing, lifecycle ordering, recovery, PIR, or the byte encoding of authorization messages.

---

## 1. Authorization Is Separate from Mint Origin

User authorization and Mint authorization establish different facts:

1. A successful shielded challenge establishes that the responder obtained the challenge plaintext sent to the selected receiver.
2. A valid Mint self-send establishes that an entity holding the Mint spending authority authorized the Orchard action.
3. A valid Name Note establishes that its binding tuple is consistent with its on-chain note commitment.

None of these checks implies either of the other two.

The Mint must complete the required user-authorization exchange before it creates the corresponding Name Note. This is a Mint policy rule. Zcash consensus does not enforce it.

---

## 2. Authorization Address for Each Action

Each action has one authorization Unified Address:

| Action | Authorization Unified Address | Consequence |
|---|---|---|
| `claim` | The proposed Unified Address | The claimant must receive the challenge sent to the address that the claim would bind. |
| `update` | The Unified Address in the current live Name Note | A successful challenge to the current address is the only address-based authorization required. The proposed new address is not challenged. |
| `release` | The Unified Address in the current live Name Note | A successful challenge to the current address authorizes removal of the binding. |

The rule that identifies the current live Name Note will be defined by the ZNS history and ordering context. Until that rule is fixed, the Mint cannot determine the authorization address for `update` or `release` without trusting an external view of namespace state.

An authorized update may bind any syntactically valid Unified Address. The authorization exchange does not establish that the requester controls the proposed new address or that the new address can receive a payment.

Loss of access to the current authorization address prevents `update` and `release` under this rule. Any recovery procedure would be a separate authorization mechanism.

---

## 3. Unified Address Processing

The Mint must process a Unified Address under the newest production-active revision of [ZIP 316](https://zips.z.cash/zip-0316) supported by ZNS. It must continue to accept Unified Addresses valid under earlier production revisions unless a later ZNS protocol rule explicitly retires them.

A draft or withdrawn ZIP 316 revision is not production-active. Its address forms do not become valid ZNS authorization addresses merely because they are described in the ZIP repository.

For a valid Unified Address, the Mint selects the most preferred receiver type that it supports under the applicable ZIP 316 selection rule. Unknown non-mandatory items are ignored as required by that revision. An address containing an unknown mandatory item must be rejected when the applicable revision requires rejection.

The successful response applies only to the receiver selected by the Mint. It does not establish control of every receiver encoded in the Unified Address.

This construction requires the Unified Address to contain a shielded receiver supported by the Mint. A Unified Address containing no supported shielded receiver cannot receive a shielded challenge under this construction.

The whitepaper must define a ZNS activation rule before a future production revision of ZIP 316 changes Mint behavior. Without an activation rule, two Mint implementations can adopt the same ZIP revision at different times and apply different authorization rules.

---

## 4. CLAIM Sequence

The preliminary `claim` sequence is:

1. The requester sends a claim request to the Mint through a shielded memo.
2. The Mint validates the proposed Unified Address and selects a receiver under Section 3.
3. The Mint generates a challenge inside the TEE.
4. The Mint sends the challenge to the selected receiver through a shielded memo.
5. A party that recovered the challenge plaintext returns the response to the Mint through a shielded memo.
6. The Mint validates the response.
7. If the response and the remaining claim rules are valid, the Mint creates the `claim` Name Note by Mint self-send.

This exchange establishes access to the selected receiver before the claim is created. It does not establish a legal identity, entitlement to the name, or control of the other receivers in the Unified Address.

---

## 5. UPDATE Sequence

The preliminary `update` sequence is:

1. The requester sends an update request containing the name and proposed new Unified Address to the Mint through a shielded memo.
2. The Mint identifies the current live Name Note for the name.
3. The Mint validates the current Unified Address and selects a receiver under Section 3.
4. The Mint generates a challenge inside the TEE.
5. The Mint sends the challenge to the selected receiver of the current Unified Address.
6. A party that recovered the challenge plaintext returns the response to the Mint through a shielded memo.
7. The Mint validates the response.
8. If the response and the remaining update rules are valid, the Mint creates an `update` Name Note that binds the proposed new Unified Address and references the current predecessor.

The Mint does not challenge the proposed new Unified Address. Consequently, a successful update does not establish that the new address is controlled, reachable, or correctly entered.

---

## 6. RELEASE Sequence

The preliminary `release` sequence is:

1. The requester sends a release request containing the name to the Mint through a shielded memo.
2. The Mint identifies the current live Name Note for the name.
3. The Mint validates the current Unified Address and selects a receiver under Section 3.
4. The Mint generates a challenge inside the TEE.
5. The Mint sends the challenge to the selected receiver of the current Unified Address.
6. A party that recovered the challenge plaintext returns the response to the Mint through a shielded memo.
7. The Mint validates the response.
8. If the response and the remaining release rules are valid, the Mint creates a `release` Name Note that references the current predecessor.

A successful release response authorizes removal of the current binding. It does not authorize a later claim of the released name.

---

## 7. Private Authorization Accounts

The account used for public Name Notes must not carry challenges, responses, or other private Mint operations. Its full viewing key is public, so any memo sent to that account is public to every scanner holding the key.

Authorization requests and responses must use a separate Mint authorization account whose viewing authority is not published. Challenges must be sent from an account whose outgoing records are not exposed by the public Name Note full viewing key.

Account separation prevents publication through the Name Note viewing key. It does not hide network metadata from the Mint operator, the requester's wallet provider, or other infrastructure involved in submitting the transactions.

---

## 8. What a Successful Challenge Proves

A returned challenge proves access to the challenge plaintext if all of the following assumptions hold:

1. The challenge was unpredictable before the Mint generated it.
2. The challenge ciphertext was sent to the receiver selected from the authorization Unified Address.
3. The response received by the Mint contains the expected challenge value.
4. The challenge value was not disclosed through another channel.

This proof is possession of information, not proof of a Zcash spend. A holder of sufficient incoming viewing authority may recover the challenge without holding the corresponding spending key. Forwarding the challenge plaintext also permits another party to return it.

ZNS intentionally treats recovery and return of the challenge plaintext as sufficient authorization. The responder is not required to prove possession of the spending key for the selected receiver.

Consequently, a holder of sufficient viewing authority can authorize the action. A party that receives the challenge plaintext from such a holder can also return it. The protocol cannot distinguish deliberate delegation from accidental disclosure of the challenge.

---

## 9. Request Binding and Replay

An unbound passcode can be reused or substituted across requests. Preventing that attack requires the authorization exchange to identify the operation it authorizes.

The proposed challenge input consists of:

- protocol version;
- network;
- action;
- canonical name;
- current Name Note commitment, when the action has a predecessor;
- proposed Unified Address, when the action creates a binding;
- an unpredictable nonce; and
- an expiration condition.

These fields remain proposed rather than normative. The exact encoding, expiration rule, and response-consumption rule require protocol-author decisions and test vectors.

Until those rules are fixed, a successful passcode comparison cannot be claimed to authorize exactly one action. A compromised application could substitute a different name, action, address, predecessor, or network if the omitted field is not authenticated by the response.

The Mint may retry either of its outbound operations without requiring new user authorization:

1. It may retry delivery of the same challenge to the same selected receiver.
2. After a successful response, it may rebroadcast the same signed Name Note transaction.

A retry must not change the network, action, name, authorization address, proposed Unified Address, or predecessor. A change to any of those fields is a different operation and requires a new challenge.

The Mint must not create two transactions that can both publish the same authorized Name Note operation. It may construct a replacement transaction without a new challenge only after the earlier transaction can no longer enter the canonical chain.

---

## 10. TEE State and Restart Boundary

The grant design generates challenges and validates responses inside the Mint TEE. This placement protects the comparison from an operator that cannot read or modify enclave memory under the TEE assumptions.

Replay prevention requires the Mint to retain enough protected state to distinguish issued, expired, and consumed challenges. Restart behavior determines whether that state survives a Mint restart.

The protocol has not yet decided:

- whether pending challenges survive a restart;
- whether consumed-challenge state must be sealed across restarts;
- how sealed state resists rollback;
- whether a challenge expires by wall-clock time, block height, or both; or
- what happens to a pending authorization after a chain reorganization changes its predecessor.

Without rollback-resistant consumed state or a request binding that becomes unusable after one accepted transition, restoring older enclave state can make an accepted challenge valid again.

---

## 11. Third-Party Verification Boundary

The public Name Note account exposes the resulting Name Note. The private authorization account does not expose the preceding challenge exchange.

A third party can verify the Name Note commitment and the Mint self-send. Those checks do not reveal whether the Mint issued a challenge, which receiver received it, or whether the response was correct.

Public TEE attestation can bind the Mint key to reviewed enclave code only if the attestation and key-continuity rules establish that relationship. Attestation alone is not per-request evidence that a particular execution followed the authorization policy.

The protocol has not decided whether third parties must receive evidence of each authorization exchange. Adding such evidence could improve auditability but could also expose authorization metadata or link private messages to public Name Notes.

---

## 12. Consequences and Non-Guarantees

The confirmed action rule has these consequences:

- `claim` challenges the proposed Unified Address.
- `update` challenges only the current Unified Address.
- `release` challenges the current Unified Address.
- Decryption authority for the selected receiver is sufficient; spending authority is not required.
- The Mint may retry delivery of the same challenge or rebroadcast the same signed Name Note transaction without a new challenge exchange.
- The Mint must not create two transactions that can both publish one authorized Name Note operation.
- An update does not prove control or reachability of its proposed new address.
- Backward-compatible production Unified Addresses remain eligible for authorization processing.

The current construction does not guarantee:

- possession of a spending key for the selected receiver;
- control of every receiver in a Unified Address;
- correctness of an address that is not challenged;
- recovery after loss of decryption authority;
- one-time use, expiration, or replay resistance before the corresponding rules are fixed;
- survival or invalidation of pending challenges across Mint restarts;
- correct handling of a chain reorganization; or
- third-party proof that the Mint followed the challenge policy for a particular Name Note.

The grant application proposes removing user keypairs, moving the OTP service into the TEE Mint, exchanging OTP messages through shielded memos, and minting a Name Note after a correct response. It does not specify the request-binding, retry, restart, account, or per-request audit rules required to make that flow normative.

---

## 13. Unresolved Decisions

The protocol author must still decide:

1. Which challenge fields are normative and how they are encoded.
2. How challenge expiration is measured.
3. How failed attempts, duplicate responses, and concurrent requests are handled.
4. Which protected state survives a Mint restart and how rollback is detected.
5. How a chain reorganization affects a challenge bound to a predecessor.
6. Which condition proves that an earlier Name Note transaction can no longer enter the canonical chain.
7. How a new production revision of ZIP 316 becomes active in ZNS.
8. Whether ZNS rejects a future production Unified Address that contains no supported shielded receiver.
9. Whether third parties receive per-request authorization evidence.

Until these decisions are fixed, the shielded challenge is a preliminary authorization mechanism rather than a complete authorization protocol.

---

## 14. Sources and Status

The shielded passcode flow and TEE placement are derived from the [Zcash Community Grants application for ZNS](https://github.com/ZcashCommunityGrants/zcashcommunitygrants/issues/298). The application records promised scope, not a complete authorization specification.

Unified Address validation and receiver selection are derived from [ZIP 316](https://zips.z.cash/zip-0316). ZNS must pin any normative byte-level dependency to a production revision and reviewed test vectors.

The action-specific authorization addresses, the decision that an update challenges only the current address, and the use of decryption authority as the authorization threshold are decisions of the protocol author.
